# ماتریس نقش‌ها و مجوزها

**سیاست چندنقشی مصوب:** اجتماع scopeهای نقش‌های فعال در چارچوب شرکت/مستأجر؛ جزئیات معتبر و ماتریس API در [سیاست مجوزدهی](./authorization-policy.md). این ماتریس جایگزین برداشت‌های قدیمی «فقط HR assignment» برای حساب چندنقشی است.

قواعد حاکم: اجرای سمت سرور؛ scope = شرکت/واحد؛ مدیر مستقیم از snapshot درخواست؛ نقش‌های «مجاز به محرمانه» صراحتاً تعریف‌شده‌اند.
علائم: ✔ مجاز، ○ مجاز با شرط/scope، ✖ ممنوع.

## ماتریس خروجی فایل

Export مجوز تازه ایجاد نمی‌کند و از همان scope سمت‌سرور API خواندن متناظر استفاده می‌کند.

| Dataset | کارمند | مدیر مستقیم | HR دامنه‌دار | گزارش‌خوان ارشد | مدیر سامانه |
|---|---|---|---|---|---|
| `employees` | فقط خود | تیم مستقیم؛ خود با `scope=me` | فهرست کارکنان scope | ✖ | فهرست سراسری کارکنان |
| `leave-requests` | درخواست‌های خود | درخواست‌های تیم؛ `scope=team` | درخواست‌های scope | ✖ | ✖ |
| `employee-balances` | خود | یک کارمند مجاز در API مانده | یک کارمند داخل scope | ✖ | ✖ |
| `absences`, `balances`, `trends`, `process-health` | ✖ | ✖ | aggregate scope | aggregate scope با حداقل گروه | ✖ |
| `bradford` | ✖ | ✖ | scope HR و صفحه‌بندی‌شده | ✖ | ✖ |

`employee` فقط فیلتر محدودکننده در queryset مجاز است؛ company/tenant دلخواه پذیرفته نمی‌شود. اطلاعات درخواست محرمانه با همان serializer سمت‌سرور و پیش از CSV/XLSX redacted می‌شود. گزارش اجرایی هیچ شناسه یا ردیف فردی صادر نمی‌کند و حداقل گروه و سرکوب گزارش جاری را حفظ می‌کند. خروجی به ۱۰٬۰۰۰ ردیف CSV یا ۵٬۰۰۰ ردیف XLSX و بازه اختیاری ۳۶۶ روز محدود است؛ Bradford محدودیت پنجره و صفحه‌بندی خودش را دارد. همه خروجی‌ها ممیزی می‌شوند، ولی AuditEvent محتوای ردیف‌ها یا عبارت خام جست‌وجو را ذخیره نمی‌کند.

## ردیف‌های امنیتی ثابت
- تغییر manager یا نقش فوراً اثر می‌کند (بدون کش بلندمدت).
- مدیر بدون رابطه مستقیم به درخواست دسترسی ندارد؛ شناسه‌ی غیرمجاز → 404 (نه 403) برای جلوگیری از افشای وجود.
- مدیر سامانه به‌طور پیش‌فرض داده مرخصی افراد را نمی‌بیند (تفکیک وظایف).
- `LeaveType` کاتالوگ سراسری است و شرکت/tenant ندارد. مجوز `leave_type.global.manage` فقط از نقش `admin` سراسری (و superuser مورداعتماد که در authorization به admin نگاشت می‌شود) مشتق می‌شود؛ هیچ تخصیص HR آن را ایجاد نمی‌کند. ایجاد/ویرایش/غیرفعال‌سازی نیازمند دلیل است و هر موفقیت با before/after، actor، timestamp و `X-Correlation-ID` اختیاری ممیزی می‌شود.
- `leave_type.read` مستقل از مجوز نوشتن است: HR دارای scope فعال انواع فعال را می‌خواند؛ کارمند/مدیر مستقیم انواع فعال و requestable را؛ admin همه انواع را. exec-only و ناشناس رد می‌شوند. جزئیات قرارداد و طول دلیل در [راهنمای فعلی انواع مرخصی](./leave-types-guide-fa.md) است.
- اگر کسب‌وکار به انواع مرخصی مختص شرکت نیاز دارد، باید تصمیم محصول/مالک داده پیش از بازطراحی tenant-specific گرفته شود. طرح نیازمند `company` FK، یکتایی کلید در دامنه مناسب و بازبینی FKهای LeaveRequest/LeaveEntitlement، تداخل کلیدها، انتقال امن داده و رفتار انواع سراسری است؛ این تغییر با مدل فعلی شبیه‌سازی نشده است.
- حساب غیرفعال/سرویس/مهمان: ورود ممنوع یا is_employee=false.

## ترکیب HR و Manager

در حساب HR+Manager، رکوردهای self، direct report همان شرکت و HR assignment فعال اجتماع می‌شوند؛ این union در فهرست کارکنان/درخواست، balance، گزارش‌های مجاز، coverage و Export اعمال می‌شود. قابلیت عملیاتی endpoint همچنان لازم است: Manager به‌تنهایی Entitlement adjustment یا گزارش HR را انجام نمی‌دهد و HR assignment، مجوز global نمی‌شود. داده محرمانه فقط در assignment HR دیده می‌شود؛ Manager خارج از assignment نمی‌تواند نوع/دلیل/پیوست confidential را ببیند. پیوست غیرمحرمانه برای direct manager همان شرکت قابل دسترسی است.

RoleAssignment غیرفعال یا منقضی scope نمی‌دهد؛ `expiresAt` اختیاری و timezone-aware است. Manager از رابطه زنده/manager snapshot در درخواست مشتق می‌شود. تغییرات نقش و انقضا Audit می‌شوند.
